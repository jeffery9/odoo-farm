## 1. 战略背景与核心挑战 (Vision & Challenges)

在 Odoo 19 平台上构建一个能够同时支撑“种植、畜牧、水产、深加工、农旅”全产业链的系统，其技术核心矛盾在于**“底层模型的强一致性”**与**“行业应用的高度差异化”**。

### 1.1 公共模型的“身份分裂”
受影响底座：`mrp.bom` (配方), `mrp.production` (任务), `stock.lot` (批次)
-   **数据污染风险**：养鱼用户不应在搜索中看到化肥配方。
-   **UI 臃肿风险**：在单一视图中通过 Invisible 逻辑控制上百个字段会导致 XML 崩溃。
-   **算法互斥风险**：不同行业对“完工”和“成本”的计算公式完全不同。

## 2. 方案 1 原理：标准类继承 (Standard Inheritance)

### 2.1 技术实现原理
使用原生 `_inherit = 'base.model'` 机制。

*   **数据库层 (SQL)**：
    -   所有扩展字段（如 `fodder_ratio`, `brix_level`）都会被添加进原生的数据库表（如 `mrp_bom`）。
    -   这会导致数据库单表变得极其冗长（宽表）。
*   **方法调用链**：
    -   所有行业的逻辑都堆叠在同一个 Python 函数中，通常伴随着大量的 `if industry == 'livestock':` 判断。
*   **ORM 处理**：
    -   Odoo 启动时会动态将所有继承类合并为一个单一的内部模型类。

### 2.2 评估结论：弃用
- **(+) 优点**：原生兼容性 100%，报表无需修改。
- **(-) 缺点**：维护地狱。单表字段数爆炸（可能突破 200+），严重影响索引性能和代码可读性。

---

## 3. 方案 2 原理：原型继承 / 物理克隆 (Prototype Inheritance)

### 3.1 技术实现原理
使用 `_name = 'new.model'`, `_inherit = 'base.model'` 机制。

*   **数据库层 (SQL)**：
    -   系统会克隆基类的所有字段，创建一个**全新的、完全独立的物理表**（如 `aquaculture_bom`）。
    -   此表与原生表在数据库层面**没有任何物理关联**。
*   **方法调用链 (Method Chain)**：
    -   Python 方法代码被复制到了新模型。
    -   **核心危机：逻辑漂移**。若原生方法包含 `self.env['mrp.bom'].search(...)` 这种硬编码引用，克隆体在执行时会错误地跳回原表查找数据，导致行业数据对引擎“不可见”。
*   **ID 空间管理**：
    -   克隆表拥有自己的一套 ID 序列。这导致原生库存（Picking）或报表（Analytic）无法识别这些 ID，业务链路彻底断裂。

### 3.2 评估结论：弃用
- **(+) 优点**：100% 的物理隔离，UI 极致纯净。
- **(-) 缺点**：生态断裂。选择此项意味着要重写整个 Odoo 的财务、库存和 MRP 计算引擎。

---

## 4. 方案 3 原理：影子方法 / 逻辑代理 (Shadow Mapping)

### 4.1 技术实现原理
行业模型作为 Facade，后台同步维护一个隐藏的“影子”原生记录。

*   **架构层级**：
    - **UI 层**：用户操作前端行业模型。
    - **同步层**：重写 `create/write`，在后台同步操作一个 `mrp.bom` 影子记录。
    - **代理层**：将核心确认动作（Action Confirm）委派给影子对象执行。
*   **逻辑原理**：
    - 试图在不破坏 ID 空间的前提下获得方案 2 的洁净度。

### 4.2 评估结论：弃用
- **(-) 缺点**：工程实现极其复杂。需要处理双向 ID 绑定、事务锁、删除级联等。ID 数量会翻倍，增加数据库存储成本。

---

## 5. 方案 4 原理：委托继承 (Delegation Inheritance - ISL 架构) 🏆

### 5.1 技术实现原理
利用 Odoo 的 `_inherits = {'base.model': 'base_id'}` 机制（类似于 `res.users` 对 `res.partner` 的多态继承）。

*   **数据库层 (SQL) - 父子指针**：
    - **子表** (`livestock_bom`)：仅存储行业私有扩展字段。
    - **父表** (`mrp_bom`)：存储所有行业共用的核心字段（产品、数量、单位）。
    - **物理关联**：子表通过一个 `mrp_bom_id` 外键与父表建立 1:1 的指针关联。
*   **ORM 层 - 字段穿透与重定向**：
    - Odoo ORM 实现了底层的 `getattr/setattr` 重定向。
    - 当代码访问 `livestock_bom.product_id` 时，ORM 感知到该字段在父表中，会自动执行跨表读取。
    - 在视图（XML）中，子模型可以直接声明父字段名，无需感知跨表。
*   **逻辑层 - 多态方法委派**：
    - 子模型通过 `super()` 调用基类方法。
    - 流程：`子类行业逻辑` -> `super() 触发基类标准流` -> `子类后续处理`。这保证了 Odoo 标准估值与库存逻辑 100% 被复用。

### 5.2 评估结论：定案选型
- **(+) 优点**：实现了物理分表的极致洁净度，同时保留了 ID 在原生生态系统中的合法性与统一性。
- **(+) 核心价值**：支持无限的横向行业扩展，每个行业 App 像独立产品一样轻盈。

## 6. ISL 架构实施军规与准则 (ISL Code of Conduct)

### 6.1 动态感知编写规范 (Contextual Awareness)
严禁在算法层写死模型名。
- **WRONG**: `self.env['mrp.bom'].search(...)`
- **RIGHT**: `self.env[self._name].search(...)` 确保逻辑作用于正确的物理表。

### 6.2 独立视图准则 (Independent View Rule)
- 严禁在行业子模块中使用 `inherit_id` 修改基类 XML。
- 必须定义**完全独立的 Form 视图**，利用字段穿透展示父类数据。

### 6.3 行业激活原则 (Creation Flow)
- 业务必须从“行业 App”端发起。禁止在后台直接修改父表记录，以确保行业元数据的完整性。

## 📎 附录：深度对话与逻辑推演全记录 (Discussion Archive)

### Q1：关于原型继承复用逻辑的探讨
**用户**：原型继承能复用业务逻辑吗？
**推演**：代码能跑，但上下文断裂。硬编码的模型字符串是原型继承的“癌症”。如果不进行大规模的泛型重构，逻辑会错误地跳回原表。

### Q2：影子模式是否具备可行性？
**用户**：影子记录能保留原生逻辑吗？
**分析**：理论可行，但影子模式会导致 ID 空间爆炸且事务处理极其复杂。委托继承（_inherits）是 Odoo 框架原生提供的、经过数据库优化的“官方版影子模式”，效率更高。

### Q3：委托继承在财务层面的透明度
**探讨**：分表会不会导致财务看不到数据？
**结论**：不会。ISL 架构下，所有行业记录在底层父表都有一个“投影”。财务经理直接打开标准报表即可穿透所有行业，实现“前端分治，底层合一”的终极目标。

## 7. ISL 架构演进 V3.0：底座化与自动化 (Refinement & Automation)

### 7.1 插件化底座 `farm_mrp`
为了彻底解决行业模块间的耦合，我们抽象出了 `farm_mrp` 模块。
- **职责**：提供 Mixin、钩子方法和通用的重定向逻辑。
- **解耦原理**：父类不再通过 `if/else` 判断行业，而是调用 `_get_isl_model()` 钩子。各垂直模块通过 `_inherit` 覆盖此方法。

### 7.2 影子记录自动实例化 (Automatic Instantiation)
解决“创建流断层”风险。
- **机制**：在 `mrp.production/bom` 的 `create` 方法中注入逻辑。如果 `industry_type` 命中，自动 `create` 对应的 ISL 影子记录。
- **价值**：确保了无论是手动创建、MRP 运算还是 API 导入，ISL 扩展数据始终与底座同步。

### 7.3 批次反射解耦 (Decoupled Reflection)
- **实现**：`stock.lot` 定义 `_get_isl_summary_parts` 钩子。
- **效果**：养殖模块注入重量/品种，种植模块注入地块，互不干扰，底座仅负责聚合显示。
