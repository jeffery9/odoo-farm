# Odoo 19 农场管理系统：开发规范 (Development Conventions)

本规范旨在确保系统在 Odoo 19 社区版环境下的高质量交付，强调“测试驱动”、“用户至上”与“价值导向”。

## 1. 核心技术栈与环境
- **平台**: Odoo 19 社区版 (AGPLv3 开源协议)。
- **版权说明**: 允许商用与分发，SaaS 部署需公开源码。
- **语言**: Python 3.12+, JavaScript (Owl Framework), XML (QWeb)。
- **依赖管理**: 严格限制使用 Odoo 企业版组件。优先选择 OCA (Odoo Community Association) 模块。
- **运行环境**: 必须适配移动端浏览器（Responsive Web Design）。

## 2. 原子模块组合原则 (Atomic Module Composition Principle)
- **模块原子性**: 每个模块实现单一职责，专注于特定业务领域（如：`farm_field_crops` 专注大田作物，`farm_livestock` 专注畜牧养殖）
- **组合灵活性**: 通过 `res.config.settings` 配置界面，用户可根据实际需求启用/禁用特定行业模块
- **依赖清晰性**: 模块间依赖关系明确，遵循 `farm_core` → `business_modules` → `integration_modules` 的层级结构
- **功能叠加性**: 不同行业模块可根据业务需要进行组合，支持复合型农业经营（如：茶业 + 观光、养殖 + 加工 + 销售）
- **配置驱动**: 模块启用后自动安装依赖，用户界面根据启用模块动态调整显示内容
- **业务隔离**: 每个行业模块的数据流、业务逻辑和权限控制相互隔离，避免业务干扰

### 2.1 原子模块设计模式
- **单一职责**: 每个模块只处理特定领域的业务逻辑
- **接口标准化**: 模块间通过标准化接口进行通信和数据交换
- **可插拔性**: 模块可以独立安装、卸载，不影响其他模块的正常运行
- **配置化**: 通过系统配置实现模块的启用/禁用，而非硬编码

### 2.2 组合应用模式
- **垂直行业组合**: 如 `farm_field_crops` + `farm_agritourism` 实现农旅结合
- **产业链组合**: 如 `farm_livestock` + `farm_agricultural_processing` 实现养殖加工一体化
- **技术服务组合**: 如 `farm_iot` + 任何行业模块提供物联网支持

### 2.3 实现约束
- **模型扩展**: 新模块通过继承机制扩展现有模型，避免数据结构重复定义
- **权限控制**: 每个模块定义自身的用户组和访问权限，通过组合形成复合权限
- **界面适配**: 模块启用后动态添加菜单项、视图和操作按钮
- **数据安全**: 模块间的数据访问需遵循权限控制规则，确保数据隔离

## 3. TDD (测试驱动开发) 规范
所有功能模块必须包含完整的自动化测试，严禁“裸奔”交付。

- **测试位置**: 每个模块下的 `tests/` 目录。
- **执行原则**:
    - **红-绿-重构**: 先写测试用例（红），实现代码使其通过（绿），最后优化结构（重构）。
    - **业务覆盖**: 核心算法（如：饲喂计算、养分平衡、休药期检查）必须达到 100% 逻辑覆盖。
- **命令示例**: `odoo-bin -c <config> -i <module> --test-enable --stop-after-init`

## 4. UI/UX: 用户友好第一 (User-Friendly First)
针对农场现场作业环境（强光、单手操作、戴手套）进行优化。

- **三步原则 (3-Click Rule)**: 现场工人从打开扫码界面到完成作业确认，点击次数严禁超过 3 次。
- **视图规范**:
    - **Kanban (看板)**: 所有的主要业务活动（如：农事干预、生产任务、动物批次）必须提供看板视图。卡片需包含：状态进度条、关键指标（如：日龄/湿度）、执行人头像及快速操作按钮。
    - **Pivot (透视表)**: 所有涉及数值分析的场景（如：成本分摊、产量分析、能耗统计、养分平衡）必须提供透视图，并预设合理的行/列分组及度量值（Measures）。
- **移动端优先**: 
    - 优先设计 `list` 和 `form` 的移动端视图。
    - 重要按钮使用 `btn-primary` 或 `btn-lg`，高度不少于 48px。
- **状态感知**: 任务进度、环境异常（IIOT）需通过高对比度颜色（红/橙/绿）即时反馈。
- **输入简化**: 尽可能使用扫码（QR/Barcode）、拍照、语音转文字，减少键盘输入。

## 5. 价值交付与代码逻辑
- **原子化提交**: 每次提交必须对应一个或多个 `US-X` 编号的用户故事，并在 Commit Message 中注明。
- **业务语义化**: 变量名、模型名必须具有明确的农业业务含义（如：用 `land_parcel_id` 而非 `location_id`）。
- **解耦设计**:
    - 核心业务逻辑封装在 `models` 的独立方法中，方便测试。
    - 计算密集型任务（如全量 MRP 运算）需通过 `ir.cron` 异步处理。

## 6. 安全与合规
- **不可篡改性**: 涉及有机认证、防疫用药的关键记录，必须启用 Odoo `mail.tracking.value` 审计追踪。
- **数据一致性**: 严禁在代码中直接修改 `stock.valuation.layer` 等财务核心底层，必须通过标准库存移动方法触发。

## 7. 模块结构约定
所有模块存放在 ./ 目录下，遵循以下结构：
```text
farm_<module_name>/
├── __init__.py
├── __manifest__.py
├── models/         # 业务模型与算法
│   ├── __init__.py
│   ├── model_1.py  # 单一职责模型文件
│   ├── model_2.py  # 单一职责模型文件
│   └── ...
├── views/          # 视图与菜单
│   ├── model_1_views.xml  # 与特定模型相关的视图
│   ├── model_2_views.xml  # 与特定模型相关的视图
│   ├── menu.xml          # 菜单定义
│   └── ...
├── security/       # 权限(ir.model.access.csv)
│   ├── ir.model.access.csv  # 模型访问权限
│   ├── res_groups.xml       # 用户组定义
│   └── ...
├── data/           # 预设数据(防疫模版、品种分类)
│   ├── initial_data.xml
│   └── ...
├── tests/          # TDD 测试用例
│   ├── __init__.py
│   ├── test_model_1.py
│   ├── test_model_2.py
│   └── ...
└── static/         # CSS/JS (Owl 组件)
    └── ...
```

- **多语言与编程语言 (i18n)**：
    - **英文编程**：为兼容 Odoo 原生 i18n 翻译机制，所有模型名、字段名、方法名及 Python 代码中的字符串硬编码必须使用**英文**。
    - **中文备注**：代码注释、业务逻辑说明及开发者备注可以（且建议）使用**中文**，以确保团队对复杂农业逻辑的准确理解。
    - **i18n 驱动**：前端 UI 的中文展示必须通过模块下的 `i18n/` 翻译文件（.po）实现，严禁在 XML 视图或 Python string 属性中直接硬编码中文。

## 8. 代码组织规范
- **小文件原则**: 代码应分散在更小的文件中，每个文件承担単一职责。**强制要求单个 Python 文件行数不超过 500 行**。
- **单一职责原则 (SRP)**: 每个类、方法或模块应只有一个改变的理由
- **紧密联系例外**: 功能紧密相关的代码可保留在同一文件中
- **模型分离**: 每个主要模型应有独立的 Python 文件
- **视图分离**: 每个模型的视图应有独立的 XML 文件
- **权限分离**: 用户组和权限规则应有独立的 XML 文件
- **测试分离**: 每个功能模块应有独立的测试文件
- **DRY原则**: 遵循"Don't Repeat Yourself"原则，避免代码重复
- **KISS原则**: 保持代码简单直接，避免过度工程化
- **YAGNI原则**: "You Aren't Gonna Need It"，只实现当前需要的功能

## 9. 命名规范
- **模型文件**: 使用 `snake_case`，如 `cooperative_entity.py`, `farm_entity.py`
- **视图文件**: 使用 `model_name_views.xml` 格式，如 `cooperative_entity_views.xml`
- **测试文件**: 使用 `test_model_name.py` 格式，如 `test_cooperative_entity.py`
- **权限文件**: 使用 `model_name_security.xml` 格式，如 `cooperative_security.xml`
- **避免冗余后缀**: 禁止在文件名中使用冗余的后缀如 `management`, `extension`, `handler`, `controller` 等，除非它们能明确表达模型的特定职责。例如：
  - ❌ `biological_asset_management.py` → ✅ `biological_asset.py`
  - ❌ `land_location_management.py` → ✅ `land_location.py`
  - ❌ `activity_operation_management.py` → ✅ `activity_operation.py`
  - ❌ `user_extension.py` → ✅ `user.py` 或更具体的名称
  - ❌ `data_handler.py` → ✅ `data_service.py` 或直接 `data.py`（如果职责明确）

## 10. 模块依赖规范
- **显式依赖**: 在 `__manifest__.py` 中明确定义所有依赖
- **最小依赖**: 每个模块只依赖必需的其他模块
- **避免循环依赖**: 确保模块间无循环依赖关系
- **依赖层级**: 遵循 `farm_core` (基础层) → `farm_agri_science` (科学层) → `business_modules` (应用层) 的严格分层架构。
    - **基础模块** (如 `farm_core`) **严禁**依赖上层业务模块 (如 `farm_greenhouse`)。
    - **上层模块**通过继承 (`_inherit`) 扩展基础模块功能，实现 Inversion of Control (控制反转)。
    - 若基础层需调用上层逻辑，必须在基础层定义抽象钩子 (Hook)，由上层模块覆盖实现。

## 10. 农业业务逻辑规范 (Agricultural Business Logic)

### 10.1 农业数据模型
- **地块管理 (Land Parcel)**: 使用 `farm.field` 模型表示地块，包含 GIS 坐标、土壤类型、面积等属性
- **批次管理 (Batch/Lot)**: 农业产品必须建立完整的批次追溯链，从种子/苗种到收获到加工
- **生长周期 (Growth Cycle)**: 每个作物/动物必须记录完整生长轨迹，包含生物阶段、环境条件等
- **投入品管理 (Inputs)**: 肥料、农药、饲料等投入品需记录成分、用量、使用时间及休药期

### 10.2 农业算法与计算
- **养分平衡计算**: 系统自动计算施肥前后土壤养分变化，确保合理施肥
- **生长模型**: 基于品种特性、环境条件预测作物生长周期及产量
- **成本核算**: 自动分摊投入品、人工、设备等成本到具体地块和批次
- **合规检查**: 自动验证投入品使用是否符合有机认证、休药期等要求

### 10.3 农业术语标准化
- **业务术语**: 统一使用农业标准术语，如"播种"、"移栽"、"收获"、"配种"、"分娩"等
- **计量单位**: 农业场景使用标准计量单位，如亩、公顷、公斤、吨等
- **生物阶段**: 植物使用"苗期"、"花期"、"成熟期"；动物使用"幼龄期"、"生长期"、"产奶期"等

## 11. 移动端与现场作业规范 (Mobile & Field Operations)

### 11.1 离线优先设计
- **离线支持**: 移动端必须支持完全离线操作，数据在网络恢复后自动同步
- **缓存策略**: 关键数据（如地块信息、任务列表、模板）预先缓存至本地
- **冲突处理**: 网络恢复后处理数据冲突，支持版本合并或人工选择

### 11.2 现场环境适应性
- **强光优化**: 界面使用高对比度设计，在强光下仍可清晰辨识
- **大屏操作**: 重要功能按钮尺寸≥48px，适应戴手套操作
- **快速录入**: 优先使用扫码、语音识别、拍照等方式，减少键盘输入

### 11.3 证据存证
- **地理水印**: 所有现场操作自动记录GPS坐标及时间戳
- **拍照存证**: 现场操作支持拍照上传，图片自动关联业务对象
- **行为审计**: 记录所有现场操作的完整审计轨迹

## 12. IoT 与传感器集成规范 (IoT Integration)

### 12.1 设备管理
- **设备注册**: IoT设备需通过统一接口注册，包含设备类型、安装位置、校准信息
- **数据采集**: 支持 MQTT、HTTP、Modbus 等标准协议，适应不同设备类型
- **状态监控**: 实时监控设备在线状态、数据质量、电池电量等

### 12.2 数据处理
- **时间序列**: 传感器数据按时间序列存储，支持插值、平滑等处理
- **异常检测**: 自动检测传感器数据异常，触发告警或数据清洗
- **数据融合**: 多传感器数据融合处理，提高数据准确性

### 12.3 自动化控制
- **规则引擎**: 基于传感器数据自动执行预设规则（如自动灌溉、通风）
- **联动控制**: 多设备间可实现联动控制，提高自动化水平
- **安全机制**: 自动化控制具备安全边界，防止误操作

## 13. 农业合规与质量控制规范 (Compliance & Quality)

### 13.1 认证管理
- **有机认证**: 记录转换期、投入品使用、隔离措施等有机认证要求
- **可追溯性**: 从种子到消费者全程追溯，记录所有关键节点
- **审计准备**: 自动生成合规报告，支持第三方审计

### 13.2 质量控制
- **质量检查点**: 设置关键质量检查点，记录检查结果和处理措施
- **不合格品管理**: 不合格品自动锁定，阻止进入下一环节
- **预警机制**: 基于质量数据建立预警机制，提前发现潜在问题

## 14. 测试与验证规范 (Testing & Validation)

### 14.1 农业场景测试
- **算法验证**: 对核心农业算法进行验证测试，确保计算准确性
- **业务流程**: 验证完整农业业务流程，从种植到收获到销售
- **合规检查**: 验证合规性检查功能的准确性

### 14.2 移动端测试
- **离线测试**: 验证离线功能的完整性和数据同步机制
- **设备兼容**: 测试主流移动设备的兼容性
- **网络切换**: 验证网络不稳定环境下的功能表现

### 14.3 IoT 集成测试
- **设备连接**: 验证不同IoT设备的连接和数据采集
- **数据质量**: 验证传感器数据处理和异常处理机制
- **自动化测试**: 验证自动化控制规则的准确性

## 15. 性能与扩展性规范 (Performance & Scalability)

### 15.1 数据处理
- **大数据量**: 支持大量农业生产数据的存储和查询
- **实时性**: 关键IoT数据处理延迟<1秒，常规数据<5秒
- **批处理**: 支持批量数据处理，避免单点性能瓶颈

### 15.2 并发支持
- **用户并发**: 支持多用户同时操作，特别是在收获季节等高峰期
- **设备并发**: 支持大量IoT设备同时连接和数据上传
- **事务处理**: 确保高并发下的数据一致性

## 16. 数据备份与安全规范 (Backup & Security)

### 16.1 数据安全
- **敏感数据**: 农业生产数据、财务数据等需加密存储
- **访问控制**: 严格的数据访问权限控制，遵循最小权限原则
- **审计日志**: 记录所有数据访问和修改操作

### 16.2 备份策略
- **定期备份**: 生产数据每日备份，关键数据实时备份
- **异地备份**: 重要数据需异地备份，防止单点故障
- **恢复测试**: 定期测试数据恢复流程，确保备份有效性

## 17. 算法文档引用 (Algorithm Documentation)

### 17.1 算法设计原则
- **准确性**: 所有农业算法必须经过验证，确保计算结果的准确性
- **可复现性**: 算法实现应保证相同输入产生相同输出
- **性能优化**: 算法应考虑大数据量处理的性能需求
- **可解释性**: 算法逻辑应清晰可理解，便于维护和调试

### 17.2 核心算法参考文档
- **养分平衡算法**: 参考 `docs/algorithms/NUTRIENT_BALANCE_ALGORITHM.md`
  - 计算施肥前后土壤养分变化
  - 推荐最优施肥方案
  - 考虑作物需求和土壤条件
- **生长预测模型**: 参考 `docs/algorithms/GROWTH_PREDICTION_MODEL.md`
  - 基于品种特性预测生长周期
  - 结合环境条件预测产量
  - 考虑生长阶段转换规则
- **成本核算算法**: 参考 `docs/algorithms/COST_CALCULATION_ALGORITHM.md`
  - 自动分摊投入品成本
  - 计算人工和设备成本
  - 支持多维度成本分析
- **休药期计算**: 参考 `docs/algorithms/WAITING_PERIOD_CALCULATION.md`
  - 基于投入品类型计算休药期
  - 自动检查收获时间合规性
  - 生成合规性报告

### 17.3 算法文档结构
每个算法文档应包含以下内容：
- **算法目的**: 明确描述算法的业务目标
- **输入输出**: 详细定义算法的输入参数和输出结果
- **算法流程**: 用流程图或伪代码描述算法逻辑
- **业务规则**: 说明算法遵循的业务规则和约束条件
- **验证方法**: 描述算法验证和测试的方法
- **性能指标**: 定义算法性能的评估标准

## 19. Git 发布与推送规范 (Git Release & Push Conventions)

为了确保代码仓库的安全与发布版本的纯净性，所有开发者必须严格遵守以下推送规约：

- **dev 分支禁推原则**：`dev` 分支仅用于本地开发、实验以及包含完整文档的历史记录。**严禁将 `dev` 分支推送到远程仓库（GitHub/GitLab）**。
- **发布分支唯一性**：远程仓库只接受发布分支（如 `19.0`）。所有代码的发布必须通过 `dev` 到 `19.0` 的过滤同步流程（参见 `RELEASE_SOP.md`）。
- **同步后再推送**：
    1. 在 `dev` 完成开发并提交。
    2. 切换到 `19.0` 并运行同步脚本（过滤掉所有 `.md` 和 `docs/`）。
    3. 仅在 `19.0` 分支执行 `git push github 19.0`。
- **强制约束**：如果发现远程仓库出现了 `dev` 分支，责任人需立即清理并重新初始化远程仓库。

## 20. 无损修改与审计律令 (Lossless Editing & Audit Mandate)

为确保系统架构的工业级严谨性，特别是在处理精密制造、配方实例化（ISA-88）等高复杂度场景时，所有开发者（包括 AI Agent）必须执行“无损开发”流程。

### 20.1 无损修改原则 (Lossless Principles)
- **物理资产保护**: 
    - 代码中的架构标记（如 `[ISA-88]`, `[LOSSLESS]`, `[US-XXX]`）及关键业务注释被视为“物理资产”。
    - **严禁移除**或在重构时简化这些标记，它们是跨系统对齐的唯一锚点。
- **禁止占位符**: 
    - 严禁在代码更新中使用 `# ... remains same ...` 或 `(此处省略)` 等占位符。
    - 必须提供完整、闭环、可直接运行的代码块。
- **注释优先级**: 在执行逻辑合并时，历史注释的保留权优先于逻辑的精简权。

### 20.2 强制审计闭环 (Read-Change-Verify Loop)
任何对代码或文档的修改必须遵循以下原子化步骤：
1.  **读 (Read)**: 修改前必须 `read_file` 全文，严禁凭借短期记忆进行模糊合成。
2.  **改 (Change)**: 
    - **增量优先**: 优先使用 `replace` 工具或 Shell 命令进行精准行级修改。
    - **5 行红线**: 超过 5 行的逻辑变动禁止使用模糊匹配替换，必须进行全量回写以确保缩进和上下文一致性。
3.  **核 (Verify)**: 写入后必须自动执行 `git diff` 或 `grep` 校验：
    - 检查历史锚点（US 编号、架构标记）数量是否减少。
    - 检查是否存在非预期的逻辑精简。

### 20.3 文档即真理 (Documentation Integrity)
- **禁止重排**: 严禁在整理 User Stories 或 Epic 时自主删除已定义的历史条目。
- **增量追加**: 新功能描述必须以增量方式追加到文档末尾或指定章节，严禁通过重写来掩盖历史版本的业务足迹。
